1Antes de empezar

Este instructivo tiene dos recorridos. Si ya trabajas habitualmente con Python, Git y un editor, te llevará unos 45 minutos y buena parte serán comprobaciones. Si vas a instalar estas herramientas por primera vez, o hace tiempo que no lo haces, calcula entre dos y tres horas y hazlo con calma: no hay ninguna prisa y el resultado es el mismo.

Lo único que importa es llegar al viernes 28 con la prueba de paso superada. Si te atascas, escribe al canal del curso con el mensaje de error completo: casi todos los problemas de instalación son de cinco minutos cuando alguien más los ha visto antes.

La vía rápida

Si ya tienes uv, Git y VS Code funcionando, empieza en «Conectar tu cuenta de GitHub». Todo lo anterior es instalación; lo que de verdad hay que hacer empieza ahí.

2Instalar uv

uv es una sola herramienta que hace lo que antes exigían cuatro: instala la versión de Python que el proyecto necesita, crea el entorno virtual, resuelve las dependencias y las fija en un archivo de bloqueo. No hace falta instalar Python por separado, ni Anaconda, ni pip, ni virtualenv.

Elegimos uv en vez de Anaconda por tres razones: es mucho más rápido, produce entornos reproducibles gracias al archivo uv.lock, y son ocho comandos en total en vez de dos ecosistemas paralelos que hay que aprender a no mezclar.

Instalación según tu sistema

Abre PowerShell (menú Inicio → escribe «PowerShell») y pega:

powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Si prefieres el gestor de paquetes de Windows, esta alternativa es equivalente:

winget install --id=astral-sh.uv -e

Importante

Al terminar, cierra PowerShell y vuelve a abrirlo. El instalador modifica el PATH y la ventana actual no se entera. Es el motivo número uno de «me dice que uv no existe».

Abre la Terminal (Cmd+Espacio → «Terminal») y pega:

curl -LsSf https://astral.sh/uv/install.sh | sh

Si usas Homebrew, esta alternativa es equivalente:

brew install uv

Importante

Al terminar, cierra la Terminal y vuelve a abrirla para que reconozca el nuevo comando.

Abre una terminal y pega:

curl -LsSf https://astral.sh/uv/install.sh | sh

Importante

Al terminar, cierra la terminal y vuelve a abrirla, o ejecuta source ~/.bashrc, para que reconozca el nuevo comando.

Comprueba que quedó instalado. Debe responder con un número de versión:

uv --version
uv 0.8.17

Y pídele la versión de Python que usaremos. Si ya la tienes, no hará nada; si no, la descarga:

uv python install 3.12

3Instalar Git

Git registra la historia del proyecto y permite que tres personas trabajen sobre el mismo código sin pisarse. En este módulo es además la evidencia de tu aporte individual dentro del equipo, así que no es opcional.

winget install --id Git.Git -e

Si prefieres el instalador gráfico, descárgalo de git-scm.com y acepta todas las opciones por defecto. Vuelve a abrir PowerShell al terminar.

La forma más simple, que además instala las herramientas de desarrollo de Apple:

xcode-select --install

O bien, con Homebrew:

brew install git

En Ubuntu, Debian o derivados:

sudo apt update && sudo apt install -y git

En Fedora:

sudo dnf install -y git
git --version
git version 2.43.0

4Configurar tu identidad en Git

Cada cambio que hagas quedará firmado con este nombre y este correo. Sin configurarlos, Git se niega a guardar nada, así que este paso no se puede saltar.

git config --global user.name "Tu Nombre Completo"
git config --global user.email "tucorreo@uptc.edu.co"

Usa el mismo correo de tu cuenta de GitHub

Si no coinciden, tus aportes aparecerán como de un desconocido y no se te atribuirán en las estadísticas del repositorio. Dado que parte de la evaluación individual sale de ahí, conviene comprobarlo ahora.

git config --get user.name
git config --get user.email

winget install --id Microsoft.VisualStudioCode -e

6Conectar tu cuenta de GitHub

Configurar tu nombre y tu correo, como acabas de hacer, sirve para firmar los cambios. Es algo distinto de autenticarte, que es lo que GitHub te va a exigir cuando envíes tu trabajo. Desde 2021 GitHub no acepta la contraseña de la cuenta desde la terminal, así que hay que conectar el equipo una sola vez.

La forma más simple y que funciona igual en los tres sistemas es GitHub CLI: se instala una vez, se abre el navegador para iniciar sesión, y a partir de ahí Git deja de pedir credenciales. Si te saltas este paso, todo funcionará hasta el momento de enviar tu trabajo, y ahí se detendrá.

Instalar GitHub CLI

winget install --id GitHub.cli -e

Cierra PowerShell y vuelve a abrirlo al terminar.

brew install gh

Si no usas Homebrew, descárgalo de cli.github.com.

sudo apt update && sudo apt install -y gh

En Fedora: sudo dnf install -y gh. Otras distribuciones en cli.github.com.

Ahora inicia sesión. Responde GitHub.com, luego HTTPS, contesta Yes cuando pregunte si quieres autenticar Git con tus credenciales, y elige Login with a web browser. Te dará un código de ocho caracteres: cópialo, pulsa Enter y pégalo en la página que se abre.

gh auth login

Comprueba que quedó conectado:

gh auth status
github.com
  ✓ Logged in to github.com account tu-usuario (keyring)
  - Active account: true
  - Git operations protocol: https

7Crear tu repositorio del curso

Conviene entender primero cómo están organizados los repositorios del módulo, porque hay tres cosas distintas y es fácil confundirlas:

RepositorioDe quién esPara qué
Plantilla del cursoDel docente. Tú solo lo lees.Contiene el punto de partida: el paquete, las pruebas y los guiones. Nunca escribes en él.
Tu repositorio personalTuyo. Lo creas en este paso.Es donde haces el Bloque 0 y tus ejercicios individuales. Aquí subes la evidencia de N1.
Repositorio del equipoDel equipo. Se crea en la sesión 1.Ahí vive el proyecto del módulo. Todavía no existe, y no hace falta para N1.

En este paso creas el tuyo personal, a partir de la plantilla. Los equipos aún no están conformados, así que el repositorio de equipo llegará más adelante.

Crear tu copia a partir de la plantilla

  1. Abre la plantilla del curso en el navegador, con tu sesión de GitHub iniciada: github.com/JeolUPTC/curso-rl-recsys

  2. Pulsa el botón verde Use this template (arriba a la derecha) y elige Create a new repository. No uses Fork ni Code → Download ZIP.

  3. Como propietario deja tu propia cuenta. Ponle de nombre rl-recsys-tu-usuario, sustituyendo tu-usuario por tu nombre de usuario de GitHub. Déjalo Public y pulsa Create repository.

    ¿Público o privado?

    Público es lo más simple: basta con entregar la dirección y el docente puede verlo. Aquí no hay nada delicado, solo tu entorno de trabajo, y con el tiempo estos repositorios forman tu portafolio. Si aun así prefieres tenerlo privado, créalo como Private y añade al docente en Settings → Collaborators → Add people, escribiendo JeolUPTC.

  4. Ahora clónalo a tu equipo. Colócate primero donde quieras guardar el proyecto:

    Sustituye tu-usuario por el tuyobash
    cd ~/Documentos       # en Windows suele ser:  cd $HOME\Documents
git clone https://github.com/tu-usuario/rl-recsys-tu-usuario.git
cd rl-recsys-tu-usuario

Atajo, si prefieres la terminal

Con GitHub CLI ya instalado, los pasos anteriores caben en una sola orden: gh repo create rl-recsys-tu-usuario --template JeolUPTC/curso-rl-recsys --public --clone. Cambia --public por --private si prefieres tenerlo privado.

No descargues el ZIP

El botón «Download ZIP» de GitHub entrega los archivos sin la historia del repositorio. La prueba de paso lo detecta y falla, porque sin repositorio no hay forma de registrar tu trabajo ni de colaborar con tu equipo. Por la misma razón, tampoco sirve clonar directamente la plantilla del docente: no podrías subir nada a ella.

8Crear el entorno y ejecutar el proyecto

Un solo comando lee pyproject.toml, descarga Python 3.12 si hace falta, crea la carpeta .venv dentro del proyecto e instala todo lo necesario. La primera vez tarda entre uno y tres minutos:

uv sync

A partir de aquí, antepón `uv run` a todo lo que ejecutes. Eso garantiza que se use el entorno del proyecto y no el Python que tengas suelto en el sistema, que es la causa más habitual del clásico «en mi máquina sí funcionaba».

uv run pytest -q
26 passed in 0.61s

Cómo vamos a organizar el código, y por qué

Conviene explicar la razón antes que la regla, porque la regla por sí sola puede parecer arbitraria.

En la mayoría de los programas, un error se manifiesta: el programa se detiene, aparece un mensaje, algo deja de funcionar. En aprendizaje por refuerzo, un error de programación no siempre impide que el entrenamiento se complete. El programa puede ejecutarse sin advertencias y producir resultados que, a simple vista, parecen razonables.

Un signo cambiado en la recompensa, un estado final mal manejado o una condición de parada equivocada no detienen nada: el agente termina su entrenamiento y devuelve una curva de aprendizaje con buen aspecto. Simplemente aprendió peor de lo que debía, y nada en la pantalla lo advierte.

Esto tiene una consecuencia directa sobre cómo hay que trabajar. Si no podemos confiar en que el programa avise cuando algo está mal, necesitamos otras formas de detectarlo: código organizado en piezas pequeñas que se puedan revisar por separado, pruebas automáticas que comprueben cada pieza, configuración registrada en archivos en lugar de escrita dentro del código, y experimentos que cualquiera pueda repetir y obtener el mismo resultado. Sin eso, un error puede pasar inadvertido durante semanas.

La regla de trabajo del curso

Los algoritmos y componentes reutilizables viven en módulos de Python, dentro de src/, con sus pruebas en tests/. Los notebooks se usan para explorar datos, analizar resultados, visualizar y documentar el razonamiento. Un notebook importa un agente desde el paquete; no lo define. En la práctica: si algo se va a ejecutar más de una vez, corresponde a un módulo.

Esto no significa que los notebooks sean una herramienta inferior. Cumplen un propósito distinto y muy valioso: permiten inspeccionar un resultado intermedio, probar una idea en segundos, ver una gráfica junto al razonamiento que la explica. Ese trabajo exploratorio es parte esencial del método y lo haremos en notebooks durante todo el curso. Lo que no funciona bien es guardar en una celda el código del que después van a depender los resultados del proyecto.

Abre notebooks/00-bienvenida.ipynb en VS Code y ejecútalo entero cuando tengas un rato. No hay que entregar nada: es para que veas cómo funciona esa separación en la práctica, y para que el viernes 28 el entorno ya te resulte familiar.
